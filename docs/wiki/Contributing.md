# Contributing

This page covers the development workflow, testing expectations, and project conventions for PaycheckCalc.

---

## Development Workflow

1. Install the .NET 11 preview SDK pinned in `global.json`.
2. Install the MAUI workload only if working on `PaycheckCalc.App`.
3. Build a non-MAUI baseline:
   ```bash
   dotnet build PaycheckCalc.Core
   dotnet build PaycheckCalc.Shared
   dotnet build PaycheckCalc.Blazor
   dotnet build PaycheckCalc.Api
   ```
4. Run tests before changing behavior:
   ```bash
   dotnet test PaycheckCalc.Tests
   ```
5. Make focused changes. Prefer small, reviewable commits, especially in tax logic.
6. Run the relevant tests again.
7. Update README/wiki/class-diagram documentation when architecture, public behavior, project structure, or data shape changes.

For manual app checks:

```bash
dotnet run --project PaycheckCalc.Api
dotnet run --project PaycheckCalc.Blazor
dotnet build PaycheckCalc.App -t:Run -f net11.0-android
dotnet build PaycheckCalc.App -t:Run -f net11.0-windows10.0.19041.0
```

---

## Project Boundaries

- `PaycheckCalc.Core` must stay free of MAUI, Blazor, HTTP, EF Core, and persistence dependencies.
- `PaycheckCalc.Shared` owns DTOs, JSON options, merge logic, API client code, store abstractions, sync services, and entitlement abstractions.
- `PaycheckCalc.Api` owns HTTP endpoints and EF Core persistence. It references Shared, not the front-ends.
- `PaycheckCalc.App` and `PaycheckCalc.Blazor` own presentation and platform-specific storage/export behavior.
- `PaycheckCalc.Tests` should cover domain, sync, API, and export behavior.

---

## Money and Rounding

- Use `decimal` for monetary values, wages, rates, thresholds, and tax outputs.
- Do not introduce `double` or `float` into calculation paths.
- Preserve established rounding behavior unless a tax-law-backed correction requires a change.
- Round final monetary results to cents using `MidpointRounding.AwayFromZero` unless a state rule requires a different intermediate rule.
- Tests should assert explicit expected dollar amounts.

## Code Organization

Follow existing folder conventions.

### MAUI

- `Views/`
- `ViewModels/`
- `Models/`
- `Mappers/`
- `Helpers/`
- `Controls/`
- `Behaviors/`
- `Services/`

Use CommunityToolkit.Mvvm source generators consistently. Pages should stay thin; view models own state and commands. Mappers translate between domain and UI models; they should not perform business calculations.

### Blazor

- `Components/Pages/`
- `Components/Shared/`
- `Services/`
- `wwwroot/`

Keep calculation behavior in Core or Shared. Razor components should coordinate UI state and rendering, not duplicate tax or sync logic.

### API

- `Data/` for EF Core context and entities.
- `Endpoints/` for minimal API route groups.
- `Migrations/` for PostgreSQL migrations.

Use Shared JSON options for sync payloads so dynamic state inputs and enums round-trip consistently.

## Tax Logic Rules

- `PayCalculator` is an orchestrator. Do not move state-specific tax rules into it.
- Every state/DC withholding implementation should live in its dedicated state folder.
- Keep dynamic state inputs schema-driven through `Data/Schemas/*.json`.
- Do not hard-code per-state UI fields when the schema can represent them.
- Keep JSON-backed tax data data-driven when the existing architecture already uses JSON.
- If a rule appears odd, inspect matching tests before changing it.
- Comment legal/table-driven quirks clearly.

Intentional examples that should not be removed casually:

- California Method B behavior, including the existing single-status adjustment.
- Oklahoma OW-2 whole-dollar rounding behavior.
- Alabama's dependence on annualized federal withholding and dependent deductions.

## Adding or Changing State Withholding

1. Add or update `PaycheckCalc.Core/Tax/<StateName>/`.
2. Implement or update `IStateWithholdingCalculator`.
3. Add or update `PaycheckCalc.Core/Data/Schemas/<state>.json`.
4. Add or update tax-table JSON when needed.
5. Register the calculator and any data-backed helper in `AddPaycheckCalcCore`.
6. Update MAUI, Blazor, and test project data-file wiring if a new JSON file is introduced.
7. Add or update tests in `PaycheckCalc.Tests`.
8. Update documentation.

Tests should cover filing statuses, bracket boundaries, exemptions/allowances, extra withholding, pre-tax deduction effects, rounding, and state-specific premium lines.

## Budgeting and Reports

Budgeting logic belongs in `PaycheckCalc.Core/Budgeting/`.

When changing budgeting behavior, consider all affected areas:

- Core domain models.
- MAUI `BudgetViewModel` and `BudgetPage`.
- Blazor `Budget.razor`.
- Shared DTOs and stores.
- Sync API entities/endpoints.
- Tests.
- Documentation.

Recurring bills and savings goals are independent GUID-keyed sync collections. Budget reports are generated by `BudgetReportCalculator` and exported by front-end renderers. Report visibility is controlled through `IEntitlementProvider`.

---

## Sync Rules

When changing sync payloads:

- Update Shared DTOs and JSON behavior.
- Update store abstractions and implementations.
- Update the API endpoint and EF Core entity model.
- Add or update migrations.
- Update merge logic and tests.
- Update MAUI and Blazor callers.
- Update documentation.

Current budget sync includes budgets, transactions, recurring bills, and savings goals. Paycheck sync includes saved paycheck snapshots.

## Testing Expectations

Use xUnit with readable scenario-based names.

Good tests should cover:

- Federal and FICA edge cases.
- State bracket boundaries.
- Filing status differences.
- Pre-tax deduction effects.
- Rounding edges.
- Dynamic state schema behavior.
- Gross-up convergence.
- Annual projection.
- Budget summaries, recurring bills, savings goals, and reports.
- Merge behavior.
- API sync round-trips.
- Export renderers.

Expected values should come from source rules, tables, or clearly derived examples. Do not compute expected tax values with the same production helper being tested.

---

## Things to Avoid

- Do not add UI, HTTP, or persistence dependencies to Core.
- Do not place business logic in code-behind, value converters, chart drawables, or export launchers.
- Do not reload static tax JSON on every calculation.
- Do not rename tax JSON files without updating all asset/link/load/test references.
- Do not remove tests to make failures disappear.
- Do not change target frameworks or preview package versions unless the task explicitly requires it.
- Do not introduce floating-point math into money calculations.

---

## Documentation Expectations

Update documentation when changing:

- Project structure.
- Public features.
- Calculation flow.
- State coverage.
- Tax data files.
- Budgeting/report behavior.
- Sync payloads or persistence.
- Front-end navigation.
- Class/architecture relationships.

Documentation should describe the current implementation, not a planned future shape.
